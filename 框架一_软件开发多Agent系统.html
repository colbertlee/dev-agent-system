0.2 为什么需要Agent？不用Agent行不行？

方案能做什么做不到什么结论
传统IDE + 脚本自动补全、格式化、跑测试不能理解需求、不能跨步骤协调、不能自主决策不够
单个LLM对话写代码、解释代码、写测试上下文窗口有限、不能并行、没有记忆、不能调用工具不够
单个Agent（如GPT-4/Cursor）代码生成+审查+测试+文档，全能但深度有限复杂项目超过上下文窗口后需要人类切分任务；没有记忆跨会话——每次都是全新开始；无法并行执行独立任务能跑但不适合系统性开发
多Agent协作每个Agent专注一个角色、可并行、可互相审查需要编排机制、有通信开销最优解

核心论证：软件开发本质上是多角色协作（架构师、开发、测试、运维、文档），每个角色有不同的思维方式和工作模式。单个 Agent（如 GPT-4+Cursor）理论上可以覆盖全流程——事实上很多个人开发者已经在这样用了。但问题是：(1) 单 Agent 的上下文窗口是有限的，复杂项目需要人类切分任务；(2) 单 Agent 没有"角色切换"的意识——它在同一段对话里既是架构师又是码农又是测试，容易混淆思维模式；(3) 单 Agent 无法并行——架构设计完成后，编码和测试用例可以同时进行，单 Agent 只能串行。多 Agent 解决的不是"单 Agent 做不了"，而是"单 Agent 做不好"——通过角色分离让每个 Agent 的 Prompt 短而精准，通过 DAG 并行执行提升效率。如果项目很简单（单文件脚本），1 个 Agent 够用——不要为了多而多。

0.3 架构选型：为什么选DAG编排？

候选架构结构适合场景为什么选/不选
顺序流水线A→B→C→D每步严格依赖上一步不选：编码和测试用例可以并行写，顺序执行浪费时间
DAG（有向无环图）A→{B,C}→D有依赖关系但部分可并行选：架构设计完成后，编码/测试用例/文档可并行，最后汇总到代码审查
自由对话（AutoGen式）Agents自由讨论探索性问题、头脑风暴不选：软件开发需要明确的步骤和可追踪的进度，自由对话不可控
监督者模式一个Supervisor分配任务任务不确定、需要动态分配不选：个人项目任务模式固定，Supervisor是额外开销

选DAG的理由：软件开发的依赖关系是固定的（架构→编码→测试→部署），不需要动态分配。DAG能表达"编码和测试并行"这种部分依赖关系，比顺序流水线快30%，比自由对话可控。

0.7 面试官视角：关键质疑与回应

以下是一个资深 Agent 工程师/面试官会提出的尖锐问题。如果你在面试中能主动覆盖这些质疑，说明你对架构的理解远超"能跑就行"的水平。

面试官质疑本质问题你的回应框架
"DAG 里 Coder/Tester/Docs 并行，Tester 发现 Bug 需要 Coder 修改，这个回流怎么处理？" DAG 是单向的，不支持回流边 当前设计通过迭代轮次解决：Reviewer 统一审查 → 如果发现 Bug，Scheduler 发起新一轮（Architect→Coder→Tester），而非在 DAG 中加回流边。回流边会导致循环依赖，破坏 DAG 的可追踪性。代价是：每轮迭代有完整开销，而非增量修复。
"Architect 是单点，它生成的架构方案如果有问题，后面所有 Agent 都白干了吧？" 级联失败风险 确实存在。缓解措施：(1) Architect 输出后增加架构评审检查点（LLM 二次验证 + 人工确认）；(2) Reviewer 在最终审查时回溯检查架构合理性；(3) 如果迭代 3 轮仍未通过 Reviewer，触发架构重设计而非继续修补。
"LLM 生成的代码质量够用吗？你真的用这个系统开发过完整项目吗？" 实际效果验证 诚实回答：当前 LLM（DeepSeek/Claude）在简单 CRUD 模块上质量可用，复杂业务逻辑仍需人工审查和修改。系统设计目标不是"完全自动开发"，而是"AI 生成 80% 骨架 + 人工审查修改 20%"。简历上应该写"AI 辅助开发流水线"，不是"全自动开发系统"。
"6 个 Agent 的协调成本很高，一个简单项目真的需要这么多 Agent 吗？" 过度工程化质疑 取决于项目规模。对于单文件脚本，1 个 Agent 足够。对于多模块项目（如日志分析系统），DAG 的并行优势才能体现。建议：默认 2 个 Agent（Coder+Tester），项目复杂度增长后逐步加 Architect/Reviewer/DevOps/Docs。Agent 数量应该跟随需求增长，不是一开始就全上。

⚠️ 最大的劣势：级联失败

DAG 架构最危险的场景是级联失败——Architect 给出错误方案 → Coder 按错误方案写代码 → Tester 按错误方案写测试（测试还通过了！）→ Reviewer 可能也看不出问题。整个链路的错误被"合理化"了。缓解：Reviewer 的 Prompt 必须包含"独立思考"指令——不信任前面 Agent 的输出，从需求出发重新验证。

📖 鲁棒性设计原则

每个故障场景必须有"降级方案"——即使降级后功能受限，系统也不能完全崩溃。面试时说"我的系统在 LLM API 不可用时会自动切换备用模型"，比说"我的系统很健壮"有说服力 100 倍。降级方案的存在本身比降级方案的完美更重要。

1 架构总览

分层架构设计，从用户到工具的完整链路。All-in-one 单仓库，个人开发者轻松维护。

📖 学习注解：为什么要分层？

分层架构是软件工程中最经典的设计模式。在Agent系统中，分层的意义在于关注点分离：Agent层只关心"我该做什么"，不知道"其他Agent在哪"；A2A层只管通信，不管业务逻辑；MCP层只管工具调用，不知道是谁在调用。这种设计让你可以独立修改任何一层而不影响其他层。面试中经常考察"你如何设计一个可扩展的Agent系统"，答案核心就是"分层 + 协议标准化"。

📖 学习注解：Agent不是微服务

新人常犯的误区是把Agent等同于微服务。关键区别：Agent有自主决策能力（调用LLM推理），微服务只是执行固定逻辑。当你设计Agent时，核心问题是"这个Agent需要什么信息来做决策？"而不是"这个服务暴露什么API？"。面试常问"Agent和微服务有什么区别"，答案核心是：Agent = LLM推理 + 工具调用 + 记忆；微服务 = 固定逻辑 + 数据库。

3 A2A + MCP 双协议详解

这是学习Agent开发最核心的两个协议，理解它们就等于掌握了2025年Agent互操作的标准范式。

🔗 A2A Protocol Google · 2025

Agent之间沟通的语言。每个Agent发布自己的"名片"（Agent Card），其他Agent发现后即可发送任务。

  • Agent Card：JSON-LD格式的能力声明，放在 /.well-known/agent.json
  • Task Lifecycle：submitted → working → completed/failed
  • JSON-RPC 2.0 over HTTP/SSE：标准RPC调用+流式推送
  • Agent Discovery：自动发现网络中的可用Agent
  • Streaming：长时间任务通过SSE实时推送进度
  • Push Notifications：Webhook回调通知任务完成
// Architect Agent 发布的能力卡片
{
  "name": "Architect Agent",
  "url": "http://localhost:8081",
  "capabilities": {
    "streaming": true,
    "modalities": ["text", "code", "file"]
  },
  "skills": [
    { "name": "system-design" },
    { "name": "api-contract" }
  ]
}

🔌 MCP Protocol Anthropic · 2024+

Agent与外部世界交互的接口。把任何工具/API/数据库封装为MCP Server，Agent即可统一调用。

  • Tools：Agent可调用的函数，如read_file、run_test
  • Resources：文件、数据库记录等资源读写
  • Prompts：可复用的提示词模板
  • Transport：stdio（本地进程）或 SSE/HTTP（远程服务）
  • Roots：定义Agent可访问的文件系统边界
// Tester Agent 调用 MCP Tool 运行测试
const result = await mcp.callTool("run_test", {
  "test_file": "tests/test_auth.py",
  "coverage": true
});
// → {passed: 23, failed: 1, coverage: "92%"}
📖 学习注解：A2A vs MCP 的本质区别

最简单的记忆法：A2A = Agent之间的语言（同行交流），MCP = Agent的手和脚（操作世界）。更深一层：A2A解决的是"Agent协作"问题，属于水平通信；MCP解决的是"Agent能力"问题，属于垂直集成。面试中几乎必考这道题，答案核心是：A2A用于Agent-to-Agent，MCP用于Agent-to-Tool。未来可能会出现统一协议（如AGNTCY），但目前这两个是最成熟的标准。

6. 代码审查Coder → ReviewerA2A: 发送PR链接审查报告
7. 自动测试Reviewer → TesterA2A: 发送测试请求测试报告

📖 学习注解：工作流是Agent系统的"骨架"

上面的工作流看似简单，但背后有一个重要概念：DAG（有向无环图）。Agent之间的任务依赖构成了一张DAG——Architect完成设计后Coder才能开始编码，Coder提交PR后Reviewer才能审查。在实现时，Orchestrator的核心职责就是构建并执行这个DAG，确保依赖关系正确、并发得当。面试中常问"如何处理Agent间的依赖"，答案就是DAG + 拓扑排序。LangGraph的StateGraph本质上就是对这个DAG的状态管理。

6 📚 概念词典：AI Agent开发必知必会50词

以下是你作为AI Agent开发者必须掌握的核心概念。按学习难度分级，从基础到进阶。面试中的概念题基本不会超出这个范围。

LLM (大语言模型)

Large Language Model
基础必知

像GPT-4、Claude这样的AI模型，是Agent的"大脑"。Agent的所有"智能"行为本质上都是LLM在推理。温度(temperature)参数控制创造性：0=精确，1=发散。

入门级

Agent (智能体)

AI Agent
基础核心

能自主感知环境、做出决策、执行动作的AI系统。公式：Agent = LLM + 工具 + 记忆 + 规划。与聊天机器人的核心区别：Agent能"做事"，不只"说话"。

入门级

Tool Calling (工具调用)

Function Calling / Tool Use
基础必知

LLM不再只输出文字，而是输出一个结构化的函数调用请求。比如LLM输出{function:"search", args:{q:"天气"}}，由外部代码实际执行搜索。这是Agent从"说"到"做"的关键。

入门级

MCP (模型上下文协议)

Model Context Protocol
核心Anthropic

Anthropic发布的Agent工具调用标准。定义了Tool（工具）、Resource（资源）、Prompt（提示模板）三种交互方式。MCP Server是你封装的工具服务，MCP Client是你的Agent。类比：MCP就是Agent世界的"USB接口标准"。

中级

A2A (Agent间协议)

Agent-to-Agent Protocol
核心Google

Google发布的Agent互操作标准。核心理念：每个Agent发布一张Agent Card（能力名片），其他Agent通过标准JSON-RPC接口发送任务。类比：A2A就是Agent世界的"电子邮件协议"。

中级

Agent Card

Agent Card (JSON-LD)
A2A核心

A2A协议的核心概念。每个Agent在/.well-known/agent.json发布自己的JSON-LD能力描述：名称、URL、技能列表、支持的模式。其他Agent通过读取这个文件来"发现"它，然后发送任务。

中级

Orchestrator (编排器)

Agent Orchestrator
架构核心

多Agent系统的"调度中心"。职责：接收用户任务→分解为子任务DAG→根据Agent Card路由到合适Agent→并发执行→汇聚结果→返回用户。LangGraph是实现Orchestrator的主流框架。

中级

LangGraph

LangGraph (LangChain)
框架必学

LangChain生态的状态图编排框架。用图（Graph）来定义Agent工作流：节点=Agent/工具，边=数据流动，状态在节点间传递。核心优势：有状态、可检查点、支持人机交互中断。

中级

CrewAI

CrewAI Framework
框架备选

另一个流行的多Agent框架。与LangGraph的区别：CrewAI更偏向"角色扮演"风格（定义Agent角色和任务），LangGraph更偏向"状态图编排"（定义节点和边）。CrewAI上手更简单，LangGraph更灵活。

中级

Human-in-the-Loop

HITL / Human-in-the-Loop
设计模式安全

在Agent的自动化流程中插入人类确认节点。A2A协议用input-required状态实现。关键设计原则：涉及资金、删除、发布、合同的操作必须有HITL。面试必问。

中级

RAG (检索增强生成)

Retrieval-Augmented Generation
记忆必知

先搜索相关文档/知识片段，再把搜索结果作为上下文注入LLM的Prompt。解决了LLM"不知道私有知识"和"知识截止日期"的问题。Agent的工作记忆层通常用RAG实现。

中级

Embedding (向量嵌入)

Text Embedding
基础必知

把文本转化为一串数字（向量），语义相近的文本向量距离也近。这是RAG的基础：用户问题→向量→在向量数据库中找最近的文档→注入LLM。OpenAI的text-embedding-3是常用模型。

入门级

VectorDB (向量数据库)

Vector Database
存储必知

专门存储和检索向量的数据库。ChromaDB（轻量/本地）、Pinecone（云）、Qdrant（高性能）、Milvus（企业级）是常见选择。Agent的记忆系统核心依赖VectorDB做语义检索。

中级

SSE (服务器推送事件)

Server-Sent Events
通信必知

HTTP协议的一种用法：服务器持续向客户端推送数据流，而不是一次性返回响应。在Agent系统中，SSE用于：LLM流式输出（逐字显示）、A2A长任务进度推送、Agent状态实时更新。

中级

JSON-RPC 2.0

JSON Remote Procedure Call
协议通信

A2A和MCP都使用的底层通信格式。请求={jsonrpc,method,params,id}，响应={jsonrpc,result,id}。比REST更简单，比gRPC更轻量。理解这个格式是理解Agent通信的基础。

中级

StateGraph (状态图)

LangGraph StateGraph
LangGraph核心

LangGraph的核心抽象：一个有状态的图，每个节点接收状态、修改状态、传递给下一个节点。状态是TypedDict格式的Python字典，在整个工作流中不断累积和更新。

高级

自治级别 (L0-L3)

Autonomy Levels
设计安全

L0：全手动；L1：Agent建议但不执行；L2：Agent执行但需要确认关键步骤；L3：全自动（仅限安全操作）。这是Agent系统的安全骨架，每个Agent/操作都要指定自治级别。

中级

Token / 上下文窗口

Token & Context Window
基础成本

Token是LLM处理文本的最小单位（≈0.75个英文单词，≈0.5个中文字）。上下文窗口=LLM一次能"看到"的最大Token数。多Agent系统中每个Agent调用LLM都消耗Token，Token成本管理是实际开发中必须关注的问题。

入门级

FastAPI

FastAPI (Python)
框架必会

Python异步Web框架，天然支持SSE和异步处理，是Agent Server的首选。每个Agent通常是一个独立的FastAPI服务，通过A2A接口对外暴露。async/await是核心特性。

入门级

DAG (有向无环图)

Directed Acyclic Graph
算法编排

Agent任务编排的数学基础。任务=节点，依赖=边。Orchestrator通过拓扑排序确定执行顺序，出度为0的节点可以并发执行。Airflow、LangGraph都基于DAG模型。

中级

10 🎯 面试高频知识点与回答思路

以下是AI Agent开发岗位面试中最常见的问题类型和回答框架。标注了面向的级别（初级/中级/高级）。

Q1: 什么是AI Agent？它和传统的聊天机器人有什么区别？ 初级必问
回答框架：核心区别在于"能否自主行动"。聊天机器人只做"输入→输出"的单轮转换；Agent则是在一个循环中持续运行：感知(Observe)→思考(Reason)→行动(Act)→观察结果→继续。公式：Agent = LLM + 工具调用 + 记忆 + 规划。可以举例说明：聊天机器人只能回答"怎么部署Docker"，Agent可以直接帮你执行docker build和docker run。
Q2: A2A协议和MCP协议有什么区别？各自解决什么问题？ 中级必问
回答框架：A2A（Agent-to-Agent）解决的是Agent之间的通信和协作问题，由Google提出，基于JSON-RPC over HTTP/SSE，核心是Agent Card发现机制和Task生命周期管理。MCP（Model Context Protocol）解决的是Agent与外部工具的交互问题，由Anthropic提出，基于JSON-RPC over stdio/SSE，核心是Tool/Resource/Prompt三层抽象。一句话：A2A是Agent之间的语言，MCP是Agent的手和脚。
Q3: 如何设计一个安全的多Agent系统？ 高级常考
回答框架：四个层面：(1)自治级别：L0-L3分级，涉及资金/删除/发布的操作必须在L2以下（需要人工确认）；(2)Human-in-the-Loop：在关键节点插入A2A的input-required状态，暂停流程等待人类决策；(3)沙箱隔离：每个Agent在独立的Docker容器中运行，文件系统和网络受限；(4)审计日志：所有Agent的LLM调用、工具执行、A2A消息全量记录到LangSmith，可追溯。还可以提到权限模型：每个MCP Tool注册时声明需要的权限级别。
Q4: 多Agent系统中的记忆是如何设计的？ 中级常考
回答框架：三层记忆架构：(1)短期记忆（Redis）：当前会话的对话历史和上下文，TTL过期；(2)工作记忆（VectorDB + RAG）：长期的、可检索的知识，如项目规范、代码库结构、用户偏好。原理是Embedding→VectorDB→相似度检索→注入Prompt；(3)长期记忆（SQLite/PostgreSQL）：结构化的永久数据，如用户设置、历史决策记录。三层记忆由Memory Agent统一管理，通过A2A对外提供读写接口。
Q5: LangGraph的StateGraph是如何工作的？ 中级常考
回答框架：StateGraph是LangGraph的核心，它是一个有状态的有向图。节点(Node)是处理函数，接收当前状态、返回状态更新；边(Edge)定义节点间的流转，可以是条件边（根据状态决定走哪条路）；状态(State)是一个TypedDict，在整张图中传递和累积。关键特性：(1)检查点(Checkpoint)机制支持中断和恢复（用于HITL）；(2)支持条件分支和循环；(3)每个节点调用后状态自动合并。在Agent系统中，每个节点通常对应一个Agent或一个工具调用。
Q6: 如何控制Agent的Token消耗和成本？ 中级常问
回答框架：几个策略：(1)模型分层：简单任务（文档生成、格式转换）用便宜模型；核心推理（架构设计、代码生成）用高级模型；(2)提示词压缩：精简系统提示词，避免冗余上下文；(3)RAG精准检索：只注入最相关的知识片段，而非全部文档；(4)缓存LLM响应：相同输入不重复调用LLM；(5)LangSmith监控：实时追踪每个Agent的Token消耗，设置预算警报。这是实际工作中必须关注的问题。
Q7: 你如何测试一个多Agent系统？ 高级常考
回答框架：分四层测试：(1)单元测试：测试单个Agent的LLM调用逻辑，用Mock替换LLM API；(2)集成测试：测试A2A通信链路，验证Agent Card发现、Task发送/接收、状态流转；(3)端到端测试：模拟完整工作流（需求→设计→编码→测试），验证所有Agent协作产出正确结果；(4)评估测试：用标准数据集评估Agent输出质量（架构设计合理性、代码正确率），建立Benchmark基线。LangSmith的Eval功能可以用于评估测试。
Q8: 你觉得Agent开发的未来趋势是什么？ 高级/开放题
回答框架：可以从几个方向回答：(1)协议统一：A2A+MCP可能会融合或被AGNTCY等新协议取代；(2)多模态Agent：不仅处理文本，还能理解图像、音频、视频；(3)Agent操作系统：像Android/iOS一样出现Agent Runtime环境；(4)端侧Agent：在手机/PC上运行的轻量Agent（Apple Intelligence）;(5)Agent间经济系统：Agent之间形成服务市场和Token支付体系。回答时注意表达自己的独立判断而不仅是罗列趋势。

13 🏗️ 可运行的脚手架代码：从零到你的第一个Agent

以下代码专为通过Trae写代码的学习者设计。每段代码都配有「让Trae帮你写这段」的提示词和逐行中文注释。如果你无法独立写出这些代码——完全正常！这个章节就是帮你用AI工具学会的。

📖 学习注解：为什么叫"脚手架"？

脚手架（Scaffold）是建筑工程中的临时支撑结构。在编程中，它指一个最小但完整可运行的代码骨架——你可以直接复制运行，然后在此基础上改。脚手架的价值在于：不需要理解每一行才能跑起来，边跑边学。

1️⃣ 最简单的Agent：能对话也能"做事"

目标：一个Python脚本，你问它"现在几点了"，它调用工具获取真实时间而不是瞎编。约60行。

🤖 让 Trae 帮你写这段

在Trae中新建 hello_agent.py，然后输入以下提示词：

「写一个Python脚本，使用OpenAI兼容API（base_url用环境变量LLM_BASE_URL，api_key用环境变量LLM_API_KEY），实现一个简单的Agent：它有一个get_current_time工具函数（返回当前时间字符串），当用户问"几点了"或"现在时间"时自动调用这个工具。用print打印整个思考过程。」

# ===== hello_agent.py — 你的第一个Agent =====
# 【这段代码在做什么】
# 1. 设置LLM连接的"门牌号"（API地址+密钥）
# 2. 告诉LLM你有一个"工具"可以用（get_current_time函数）
# 3. 进入一个循环：用户说话→LLM思考→如果需要就调用工具→回答用户

import os, json
from datetime import datetime
from openai import OpenAI  # OpenAI的Python库，也兼容DeepSeek等国产模型

# ========== 第1步：配置LLM连接 ==========
# os.getenv() 从环境变量读取，不要把Key写死在代码里
client = OpenAI(
    api_key=os.getenv("LLM_API_KEY"),     # 你的API密钥，从环境变量读取
    base_url=os.getenv("LLM_BASE_URL"),   # API地址，DeepSeek填"https://api.deepseek.com"
)

# ========== 第2步：定义工具（Agent的"手"） ==========
def get_current_time():
    """获取当前时间。当用户问'几点了'时被Agent调用。"""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

# 这段JSON是"工具说明书"——告诉LLM这个工具叫什么、怎么用
# LLM不会真正执行函数，它只是输出"我想调用get_current_time"
tools = [{
    "type": "function",
    "function": {
        "name": "get_current_time",          # 工具名称
        "description": "获取当前的日期和时间",  # 工具说明（写清楚，LLM靠这个判断何时调用）
        "parameters": {"type": "object", "properties": {}}  # 这个工具不需要参数
    }
}]

# ========== 第3步：Agent主循环（核心！） ==========
messages = [{"role": "system", "content": "你是助手，用tools获取真实信息"}]

while True:
    user_input = input("\n你: ")
    if user_input.lower() == "quit": break
    messages.append({"role": "user", "content": user_input})

    # 发送给LLM，告诉它有哪些工具可用
    response = client.chat.completions.create(
        model="deepseek-chat",  # 学习阶段用DeepSeek，便宜
        messages=messages,
        tools=tools,               # 🔑 关键：把工具列表传给LLM
    )

    msg = response.choices[0].message

    # 判断LLM是想"说话"还是想"调用工具"
    if msg.tool_calls:  # LLM说："我要调用工具！"
        for tool_call in msg.tool_calls:
            name = tool_call.function.name
            print(f"🔧 Agent调用工具: {name}")

            # 实际执行工具（这一步是你（Python代码）做的，不是LLM）
            if name == "get_current_time":
                result = get_current_time()

            # 把工具执行结果告诉LLM
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": result
            })

        # 让LLM根据工具结果生成最终回答
        final = client.chat.completions.create(
            model="deepseek-chat", messages=messages
        )
        print(f"Agent: {final.choices[0].message.content}")
        messages.append(final.choices[0].message)

    else:  # LLM直接回答，不需要工具
        print(f"Agent: {msg.content}")
        messages.append(msg)
📖 关键理解：LLM不执行工具，你执行

这是新手最容易困惑的点。看这段代码：if msg.tool_calls 之后的逻辑。LLM只是输出了一句"我想调用get_current_time"（JSON格式），真正执行 get_current_time() 的是你的Python代码。执行完后你把结果发回给LLM，它再基于结果回答。这个「LLM说要调→你调→结果回传→LLM回答」的循环就是Agent的核心机制。

2️⃣ 两个Agent通过A2A通信

目标：Architect Agent 和 Coder Agent 通过HTTP互相发送任务。这个例子需要两个终端窗口，各运行一个Agent。

# ===== architect_agent.py =====
# 【这段代码在做什么】
# 用FastAPI创建一个Web服务（Agent = Web服务 + LLM能力）
# 它暴露了两个HTTP端点：
#   GET /.well-known/agent.json → 返回Agent名片
#   POST /tasks → 接收其他Agent发来的任务

from fastapi import FastAPI
from pydantic import BaseModel  # Pydantic：定义数据格式（结构体）
import uvicorn

app = FastAPI()  # 创建Web应用

# --- Agent Card：其他Agent通过访问这个URL来"认识"我 ---
@app.get("/.well-known/agent.json")
def agent_card():
    return {
        "name": "Architect Agent",
        "url": "http://localhost:8081",
        "skills": [{"name": "system-design"}],
        "capabilities": {"streaming": False}
    }

# --- 任务接收端点：其他Agent通过POST请求给我派任务 ---
class Task(BaseModel):  # 定义任务的数据格式
    description: str  # 任务描述字段，类型是字符串

@app.post("/tasks")
def receive_task(task: Task):
    print(f"\n📨 收到任务: {task.description}")
    # 实际系统中这里会调用LLM处理任务
    return {"status": "working", "task_id": "task-001"}

if __name__ == "__main__":
    uvicorn.run(app, port=8081)  # 在8081端口启动Web服务
# ===== coder_agent.py =====
# 【这段代码在做什么】
# Coder Agent启动后：
#   1. 用requests.get去Architect的/.well-known/agent.json"认识"它
#   2. 把Architect的地址和能力信息存下来
#   3. 发送一个POST请求给Architect派任务

import requests  # requests库：Python发HTTP请求的工具
import time

ARCHITECT_URL = "http://localhost:8081"

def discover_architect():
    """步骤1：发现Architect Agent——读取它的Agent Card"""
    resp = requests.get(f"{ARCHITECT_URL}/.well-known/agent.json")
    card = resp.json()  # 把JSON字符串转成Python字典
    print(f"🔍 发现了Agent: {card['name']}")
    print(f"   技能: {card['skills']}")
    return card

def send_task(description):
    """步骤2：向Architect发送一个设计任务"""
    resp = requests.post(
        f"{ARCHITECT_URL}/tasks",
        json={"description": description}  # Python字典→自动转JSON
    )
    result = resp.json()
    print(f"✅ 任务已提交: {result}")

if __name__ == "__main__":
    time.sleep(1)  # 等Architect先启动
    discover_architect()
    send_task("设计用户登录模块的架构")
📖 关键理解：Agent之间怎么"说话"

看完这两个文件，你会发现Agent之间的通信本质就是HTTP请求——和你用浏览器访问网页一样。A2A协议的创新不在于发明了新的传输方式，而在于标准化了"Agent名片"的格式：每个Agent都在同一个路径 /.well-known/agent.json 发布自己的能力，这样任何Agent都知道去哪找、怎么读。类比：就像所有餐厅都在同一个位置挂菜单，你不需要挨个问"你们有什么菜"。

14 🐛 常见踩坑与调试指南

Agent开发有大量"看起来对但就是跑不通"的情况。以下10个坑是我在学习和你类似的系统中实际踩过的——知道了这些，你至少能省50%的调试时间。

💡 调试黄金法则：Agent系统出问题时，从外到内排查：先看HTTP能不能通（curl测），再看LLM有没有返回（print打印），最后看工具是否真的执行了（加log）。不要一上来就怀疑LLM出错了——80%的情况是网络/环境/格式问题。
#踩坑现象原因解决方案
1LLM返回的不是有效JSON，tool call格式错误用了不支持tool calling的模型（如旧版小模型）换用DeepSeek-Chat / GPT-4o-mini（都支持标准tool calling）；检查tools参数格式是否完全正确
2Agent死循环：反复调用同一个工具不停止LLM没"看到"工具的执行结果，以为调用失败了确认把tool结果以role:"tool"格式加入messages；设置最大调用次数上限（如最多调5次工具就强制终止）
3上下文溢出：聊了几轮后Agent开始"忘记"前面说了什么messages列表太长，超过了模型的上下文窗口限制messages数量（保留最近20条）；摘要压缩：让LLM把长对话总结成一段再继续
4A2A通信超时：Agent A向Agent B发任务后等了很久没响应Agent B在处理长时间任务（如调用LLM），HTTP连接超时了任务改成异步模式：POST创建任务后立即返回task_id，然后GET /tasks/{id}轮询状态；或使用SSE推送
5MCP Server连接失败："Connection refused"MCP Server没启动，或stdio模式的进程崩溃了先单独启动MCP Server确认它能运行；stdio模式加try/except捕获进程退出；SSE模式检查端口是否被占用
6中文乱码：Agent输出是乱码或空字符串Windows终端默认编码不是UTF-8；API返回的编码设置不对Python文件第一行加# -*- coding: utf-8 -*-；终端执行chcp 65001切换UTF-8；response用.encode().decode()确保编码
7API Key泄露到GitHub把key写死在代码里，git push后被扫描到用.env文件+python-dotenv库管理；.gitignore加入.env；一旦泄露立即在平台后台revoke该key
8多个Agent同时写同一个文件，数据损坏没有文件锁，两个Agent并发写冲突用threading.Lock或asyncio.Lock加锁；或让文件操作统一走一个Agent（如只让Docs Agent写文件）
9向量检索结果不相关：搜"用户登录"返回了"数据库配置"Embedding模型选错了（中英文不匹配）；chunk切得太碎中文用text-embedding-3-large或bge-large-zh；每个chunk保持200-500字；检索后加一层LLM相关性过滤
10月度API账单爆炸（¥2000+）没有设置预算和用量监控；每个Agent都在用最贵的模型学习阶段全程用DeepSeek（价格是GPT-4的1/50）；设置API平台的用量限额；LangSmith监控每Agent的Token消耗；批处理合并LLM调用

15 📝 Prompt Engineering for Agents：与聊天Prompt完全不同

给Agent写Prompt和给聊天机器人写Prompt是完全不同的两件事。Agent的Prompt需要结构化、需要告诉它"什么时候用什么工具"、需要明确"你能做什么/不能做什么"。

对比：聊天Prompt vs Agent Prompt

# ===== Coder Agent 的 System Prompt =====
# 在一个文件中定义，Agent启动时加载

"""你是一个代码实现专家Agent（Coder Agent）。
你的职责是接收架构设计文档，产出高质量的可运行代码。

== 你的工具 ==
- read_file(path): 读取项目中的现有代码，理解上下文
- write_file(path, content): 创建或覆盖文件
- run_command(cmd): 在终端执行命令（测试、lint、构建）

== 决策规则 ==
- 收到设计文档后，先 read_file 了解现有代码结构，再开始写
- 如果设计文档提到"API接口"，你必须生成对应的 FastAPI 路由代码
- 写完代码后，立即 run_command("pytest") 验证
- 如果测试失败，修复后重新运行，最多重试3次

== 你不能做什么 ==
- 不能修改架构设计文档——那是Architect的工作
- 不能部署代码到生产环境——那是DevOps的工作
- 遇到不确定的技术选型，不要自己决定，向Orchestrator请示

== 输出格式 ==
完成编码后，输出一个JSON格式的状态报告：
{
  "status": "completed" 或 "needs_help",
  "files_modified": ["文件列表"],
  "test_result": "passed" 或 "failed",
  "note": "需要人工确认的事项（如有）"
}
"""

5条Agent Prompt黄金法则

1. 说"不要做"比"要做"更重要

明确告诉Agent哪些事它不能做。比如"你不能自己编造数据，没有工具验证的信息必须说不知道"。约束比鼓励重要十倍。

2. 给工具写"使用说明书"

每个tool的description要写清楚什么时候该用、什么时候不该用。比如"search_logs: 当需要从日志中查找错误时调用，但不要用它查配置信息"。

3. 要求结构化输出

Agent的输出不仅是给人看的，更是给其他Agent解析的。在Prompt中要求输出JSON格式，方便上下游Agent自动处理。

4. 设置"护栏"

在Prompt末尾加一段：如果你尝试了3次仍无法完成任务，输出{"status":"blocked","reason":"..."}。这能防止Agent陷入死循环。

5. 用Few-shot示例

在Prompt中放1-2个"正确的输入→正确的工具调用→正确的输出"示例。LLM模仿能力极强，一个例子胜过十行规则。

面试常问："你是如何设计Agent的System Prompt的？"不要只回答"写了一段描述"，要回答："我采用结构化设计：分Role/Tools/Rules/Output四大块。Tool的description写明使用时机和禁忌。输出要求JSON便于Agent间解析。底部有失败护栏防止死循环。"这种回答展示了工程化思维。

14 🔍 资深开发者审查：遗漏与修复

以 AI Agent 资深开发者视角审查本框架的代码示例和架构设计，发现 5 个技术遗漏。

🔴 P0-1：LLM 调用无 timeout 和错误处理

⚠️ 问题

脚手架代码中 client.chat.completions.create() 没有 timeout 参数，也没有 try/except。LLM API 不可用时整个 Agent 主循环崩溃，用户看到未处理的异常堆栈。

问题代码修复方案
client = OpenAI(api_key=...)
response = client.chat.completions.create(model=..., messages=...)		 client = OpenAI(api_key=..., timeout=30, max_retries=2)
外层加 try/except Exception 返回友好错误消息

🔴 P0-2：对话历史无限增长 — 上下文窗口溢出

⚠️ 问题

Agent 主循环中 messages.append() 每轮都追加消息，但从不截断。对话 20 轮后，messages 列表的 Token 数可能超过 LLM 上下文窗口（DeepSeek 64K），导致 API 报错 context_length_exceeded。

层级方案代码思路
基础滑动窗口截断保留 System + 最近 N 轮对话：messages = [system] + messages[-N*2:]
进阶Token 计数截断用 tiktoken 计算 Token 数，超过阈值时截断旧消息
生产级摘要压缩旧对话用 LLM 总结成一段摘要，替换原始消息

🟡 P1-3：工具调用循环无最大迭代限制

Agent 主循环中 LLM 可能反复调用工具（如调 get_current_time → 看结果 → 再调 → 再看），形成无限循环。Scheduler 应设置最大迭代次数（如 10 次），超过后强制退出并返回当前结果。

🟡 P1-4：DAG 缺少错误传播机制

架构设计中 DAG 的 Coder/Tester/Docs 并行执行，但如果 Coder 失败了，Tester 和 Docs 还在运行——浪费资源。需要 取消机制：任一并行分支失败时，通知 Orchestrator 取消其他分支。

场景当前行为修复方案
Coder 生成代码失败Tester/Docs 继续运行（浪费）Orchestrator 监听分支状态，失败时发送取消信号
Tester 超时Reviewer 一直等Tester 超时后标记"测试未完成"，Reviewer 可以选择继续或重试

🟡 P1-5：缺少 /health 和优雅关闭

每个 Agent 部署后需要 /health 端点供 Docker healthcheck 使用；收到 SIGTERM 时需要优雅关闭（等待当前任务完成）。这两个是生产部署的基本要求，详细修复代码见框架五第 17 节。

📖 审查总结

5 个问题中 2 个 P0（LLM timeout + 上下文溢出）、3 个 P1（迭代限制 + 错误传播 + 健康检查）。P0 问题会在实际运行中直接导致 Agent 崩溃。框架一作为学习框架，脚手架代码是新人第一次接触 Agent 开发的参考——如果参考代码本身有问题，新人会复制这些坏习惯。修复这些问题不仅是为了"正确"，更是为了"教对了"。

框架一的 DAG 架构在稳定性方面有 3 个最关键的维度。完整代码模板见框架五第 18 节。

为什么选这 3 个维度？ 框架一是任务驱动的 DAG 流水线——Orchestrator 委派任务给 Architect→Coder→Tester→Reviewer。DAG 的特点是"前序节点失败会影响后续所有节点"，因此幂等性（防止重试导致重复代码生成）和错误传播控制最关键。此外 DAG 迭代会累积上下文，资源泄漏防护不可少。

DAG 场景的特殊性

DAG 中一个节点失败 → Orchestrator 重试 → 下游节点可能已经收到部分结果 → 重复处理会产生不一致状态。幂等性保证"重试等价于第一次执行"，是 DAG 容错的基础。

class CoderWithFallback:
    def generate_code(self, task: str) -> dict:
        # Level 1: LLM
        try:
            code = self._call_llm(task)
            return {"code": code, "source": "llm"}
        except Exception:
            pass

        # Level 2: 模板匹配
        template = self._match_template(task)
        if template:
            return {"code": template, "source": "template"}

        # Level 3: 缓存
        cached = self._cache.get(hash(task))
        if cached:
            return {"code": cached, "source": "cache"}

        # Level 4: 失败
        return {"code": None, "source": "failed", "error": "代码生成不可用"}

18 🔄 版本管理 SOP

本 SOP（标准作业程序）适用于框架一自身和由此框架开发的软件开发多Agent系统。Agent 的版本管理比传统软件更复杂——除了代码，还要管理 Prompt、模型版本、知识库、配置等"软资产"。

18.1 为什么 Agent 需要专门的版本管理？

核心问题：改了一行 Prompt → 代码审查率从 72% 掉到 58% → 你不知道是 Prompt 改了导致的 → 因为 Prompt 没进 Git。
传统软件AI Agent风险
只管理源代码管理代码 + Prompt + 模型版本 + 知识库 + 配置改了 Prompt 没记录 → 无法复现历史行为
版本 = 代码快照版本 = 代码快照 + Prompt快照 + 模型快照 + 知识库快照同一份代码 + 不同模型版本 = 完全不同结果
回滚 = git revert回滚 = git revert + 模型回退 + 知识库回退只回滚代码不回滚 Prompt = 回滚不完整
测试 = 单元测试测试 = 单元测试 + 评估数据集 + A/B 对比单元测试通过不等于 Agent 行为正确

18.2 语义化版本规范

遵循 Semantic Versioning 2.0.0，格式：MAJOR.MINOR.PATCH

版本号何时递增Agent 示例
MAJOR不兼容的架构变更、Agent 角色增删、A2A 协议变更新增 Reviewer Agent → 1.x.x → 2.0.0
MINOR新增功能（向后兼容）、新增工具、Prompt 重大优化Coder Agent 新增"自动修复"能力 → 1.1.x → 1.2.0
PATCHBug 修复、Prompt 微调（不影响输出格式）、依赖更新修复 Reviewer 对 Go 代码的误报 → 1.1.1 → 1.1.2
框架文件本身的版本：框架一的 HTML 文件也使用语义化版本——文件名末尾标注版本号：框架一_v1.2.0.html。
